# ТЗ: Fabric-мод "Chat Ping" — система меток через игровой чат

## Контекст и мотивация

Нужен клиентский мод для Minecraft, добавляющий систему меток (ping) по образцу CS/Satisfactory/современных кооперативных игр: игрок наводит курсор на точку в мире, нажимает клавишу — метка появляется у всех союзников.

Ключевое ограничение: **игра идёт на чужом сервере**, куда нельзя поставить серверную часть мода и нет доступа к инфраструктуре для внешнего бэкенда. Поэтому стандартная архитектура "мод на сервере рассылает пакеты всем клиентам" не подходит.

Решение — транспорт через обычный игровой чат, по образцу существующего мода **Client Ping** (https://modrinth.com/mod/client-ping): мод отправляет обычное текстовое сообщение в чат вида `Ping at {x, y, z}`, которое видят все игроки на сервере (даже без мода — как обычный текст). Клиенты с модом парсят входящие чат-сообщения этого формата и рисуют визуальный маркер в мире. Никакого серверного компонента, никакого внешнего сервиса, никакой привязки к конкретному серверу — всё работает на любом ванильном сервере, где не отключён/не изменён чат.

Rename: будем называть мод **Chat Ping** (рабочее имя, можно поменять в процессе).

## Референсы (изучить перед реализацией)

- **Client Ping** (modrinth.com/mod/client-ping) — главный референс по идее транспорта через чат. У него метка привязывается к Xaero's Minimap как временный waypoint — нам это НЕ нужно, у нас свой рендер.
- **Ping Wheel** (github.com/LukenSkyne/Minecraft-Ping-Wheel, CurseForge 48M+ downloads) — референс по рендеру маркера в мире (3D outline/beam, масштабирование по дистанции), но у него требуется серверная часть — нам не подходит архитектурно, смотрим только на визуал.
- **Pings by Robocraft999** (CurseForge) — Satisfactory-style outline/beacon beam в зависимости от дистанции — тоже референс по рендеру.

## Платформа

- **Loader:** Fabric
- **Minecraft:** 1.21.1–1.21.11 (нужна стратегия поддержки нескольких минорных версий — см. раздел "Открытые вопросы")
- **Mappings:** Yarn (стандарт для Fabric)
- **Тип мода:** чисто клиентский (`fabric.mod.json` → `"environment": "client"`), на сервере не требуется и не должен ничего делать, если каким-то образом окажется на сервере

## Функциональные требования

### 1. Постановка метки

- Клавиша по умолчанию: **СКМ (средняя кнопка мыши, MOUSE_BUTTON_3)**. Обязательно сделать переопределяемой через стандартный Fabric Keybinding API / Mod Menu, т.к. СКМ у многих занята под "pick block".
- При нажатии: raycast от камеры игрока вдоль направления взгляда.
  - Дистанция raycast — зафиксировать разумный дефолт (например 64 или 128 блоков) и вынести в конфиг.
  - Raycast только по блокам (`RaycastContext.FluidHandling` настроить так, чтобы не триггерилось на прозрачную жидкость некритично — уточнить на этапе реализации), сущности не учитываем (зафиксировано в предыдущем обсуждении: только блок под курсором).
  - Если raycast ни во что не попал (небо, слишком далеко) — метка не ставится, либо ставится на максимальной дистанции по направлению взгляда (решить в процессе, дефолт — не ставить).
- Результат: `BlockPos` (или точная `Vec3d` точка попадания — решить, видимо `BlockPos` для простоты и предсказуемости отображения).

### 2. Транспорт — отправка через чат

- При постановке метки клиент отправляет обычное чат-сообщение (как если бы игрок написал его сам в чат), формата:
  ```
  Ping at {x}, {y}, {z}
  ```
  (точный паттерн — см. раздел "Открытые вопросы", нужно решить на этапе реализации с учётом парсинга).
- Это должно быть именно обычное сообщение чата (`/` не нужен, не команда), чтобы:
  - Видели все игроки на сервере, в том числе без мода (просто как текст).
  - Проходило через стандартный серверный чат без серверных модов/плагинов.
- Нужно уважать клиентский rate-limit чата ванильного клиента (Minecraft сам троттлит частую отправку сообщений) — не пытаться обходить, просто не спамить.

### 3. Приём и парсинг — получатели с модом

- Мод слушает входящие сообщения чата (`ClientReceiveMessageEvents` в Fabric API, тип CHAT, не GAME_INFO).
- Парсит сообщения по паттерну, пытаясь:
  - Извлечь имя отправителя (из структуры сообщения, а не из текста — Minecraft передаёт chat-сообщения со senderом как отдельное поле/`Text` structure, где ник — часть компонента, не сырой текст; нужно опираться на это, а не парсить "Ник: текст" строкой, чтобы не ломаться на цветовых кодах §, префиксах пермишен-плагинов (LuckPerms и т.п.) и локализации).
  - Извлечь координаты `x, y, z` из текстовой части сообщения по строгому regex.
- Если парсинг не сработал (не тот формат, кто-то написал похожую фразу вручную) — сообщение просто отображается как обычный чат, никакой метки.
- Собственные исходящие ping-сообщения игрок тоже получит обратно с сервера (стандартное эхо чата) — нужно либо не дублировать обработку (т.к. маркер уже поставлен локально сразу при нажатии клавиши, до получения эха), либо дедуплицировать по (автор == сам игрок) + временному окну.

### 4. Визуализация — свой рендер

- **Без зависимости от Xaero's Minimap/Worldmap или любой другой миникарты.** Чисто свой рендер.
- 3D-маркер в мире (world-space), не HUD-оверлей с фиксированными экранными координатами (или и то, и другое — direction indicator на HUD, когда метка вне поля зрения, опционально, по образцу Ping Wheel/ping system).
- Минимум для MVP:
  - Маркер в точке попадания raycast'а (например вертикальный луч/beam от блока вверх, видимый на расстоянии — отрисовка через `WorldRenderEvents.AFTER_TRANSLUCENT` или аналогичный хук Fabric Rendering API).
  - Текстовая подпись над маркером: ник отправителя (опционально — дистанция до метки).
  - Время жизни метки — настраиваемое, дефолт несколько секунд (решить точное число в конфиге, например 10–15 сек), с затуханием (fade out) под конец.
- Рендер должен корректно работать через стены (depth test off) либо затухать через препятствия — решить на этапе реализации, что ближе к референсам (Ping Wheel рисует через стены с индикацией дистанции).

### 5. Конфигурация

- Клавиша постановки метки — переопределяемая.
- Raycast-дистанция.
- Время жизни маркера.
- Включить/выключить HUD directional indicator (если будет реализован).
- Хранение — стандартный подход Fabric (`AutoConfig` / `Cloth Config API` опционально, либо простой JSON в `config/`).

## Нефункциональные требования

- Чисто клиентская сторона, никакого серверного кода, никакой телеметрии, никаких внешних сетевых запросов.
- Не должно ломаться/спамить, если на сервере отключён чат или есть анти-спам чата — просто сообщение не уйдёт, мод не должен падать.
- Открытый исходный код, лицензия — решить (референсы используют MIT/CC0-подобные).

## Открытые вопросы для первой итерации в Claude Code

Эти пункты нужно решить/зафиксировать в начале реализации, не все ответы были даны в обсуждении ТЗ:

1. **Точный паттерн сообщения и regex парсинга.** Нужно заложить версию/префикс, чтобы отличать свои пинги от случайных совпадений в обычном чате (например уникальный непечатаемый юникод-маркер в начале строки, невидимый визуально, но однозначно идентифицируемый парсером — так делают похожие моды, чтобы не триггериться на случайные фразы игроков). Это сильно снижает ложные срабатывания по сравнению с голым `"Ping at"`.
2. **Что входит в сообщение помимо координат** — возможно стоит закодировать в том же невидимом префиксе доп. данные (например никнейм источника, если chat-сообщение ретранслируется через плагины и теряет структуру sender'а) — зависит от того, что реально приходит клиенту на целевом сервере (может быть обёрнуто в кастомный chat-формат плагина, тогда парсинг по raw-тексту надёжнее парсинга по sender-полю).
3. **Поддержка диапазона версий 1.21.1–1.21.11** — через Fabric такой разброс минорных версий обычно требует либо мультиверсионной сборки (несколько target-версий, отдельные джары), либо проверки, что Mapping/API не менялись в этом диапазоне и достаточно одной сборки под самую низкую/высокую — уточнить фактические breaking changes Fabric API между этими версиями перед тем, как обещать единый jar.
4. **Raycast при взгляде в жидкость/сквозь стекло/на entity** — финальное поведение (FluidHandling, обрабатывать ли сущности хоть как-то, даже если явно решили "только блок").
5. **Антиспам/флуд защита на уровне мода** — отдельно от ванильного client-side rate limit чата, нужен ли cooldown на клавишу постановки метки.
6. **Видимость "своей" метки** — должен ли сам игрок видеть маркер мгновенно (до получения эха от сервера) или ждать round-trip — для отзывчивости UX однозначно мгновенно, эхо от сервера тогда должно дедуплицироваться и игнорироваться для рендера (но не для текста чата — текст от сервера всё равно придёт и будет показан как обычное сообщение).

## Итог для старта разработки

Это ТЗ описывает MVP: клавиша → raycast → отправка маркированного чат-сообщения → парсинг у получателей → свой рендер маркера с ником и временем жизни, без серверной части, без внешних сервисов, без привязки к конкретному серверу, под Fabric 1.21.1–1.21.11.
